# 확장성 (Scalability)
> 데이터·트래픽·복잡도가 늘어날 때 이를 감당할 수 있는 시스템의 능력.

## 핵심
- "확장 가능하다/아니다"는 1차원 꼬리표가 아니다. "부하가 **이렇게** 늘면 어떻게 대응할 것인가?"라는 질문으로 다뤄야 한다. (보충)
- 이를 위해 먼저 **부하를 기술**하고, **성능을 측정**하는 방법이 필요하다. (보충)

## 세부 / 동작 방식
### 부하 기술: 부하 매개변수 (보충)
- 시스템마다 부하를 가장 잘 나타내는 숫자가 다르다. 예: 초당 요청 수, 읽기/쓰기 비율, 동시 활성 사용자 수, 캐시 적중률.
- 책의 예시: 트위터 홈 타임라인. 핵심 부하 매개변수는 트윗 수가 아니라 **사용자당 팔로워 분포(팬아웃, fan-out)** 였다.
  - 방식 1: 읽을 때 팔로우한 사람들의 트윗을 조인 → 읽기 부담.
  - 방식 2: 쓸 때 팔로워들의 타임라인 캐시에 미리 넣음 → 쓰기 부담. 팔로워가 매우 많은 사용자는 방식 1로 처리하는 혼합형.

### 성능 기술 (보충)
- 배치 시스템은 **처리량(throughput)**, 온라인 시스템은 **응답 시간(response time)** 이 중요하다.
- 응답 시간은 단일 값이 아니라 **분포**다. 평균보다 **백분위(percentile)** 를 쓴다.
  - p50(중앙값): 일반적인 사용자의 경험.
  - p95, p99, p999: **꼬리 지연 시간(tail latency)**. 느린 요청을 겪는 사용자는 데이터가 많은 중요 고객인 경우가 많다.
- 백엔드 여러 개를 호출하는 요청은 그중 가장 느린 호출에 묶이므로, 꼬리 지연이 사용자 체감에 증폭된다(tail latency amplification).
- 백분위는 SLO/SLA(서비스 수준 목표/협약) 정의에 쓰인다.

### 부하 대응 접근 방식
- **scale-up(수직 확장)**: 더 강력한 장비로 교체.
- **scale-out(수평 확장)**: 여러 장비에 부하를 분산.
- 여러 장비에 부하를 분산하는 아키텍처를 **비공유 아키텍처(shared-nothing architecture)** 라 한다.
- 일부 시스템은 **탄력적(elastic)** 이라 부하 증가를 감지하면 자원을 자동으로 추가한다.
- (보충) 상태 비저장(stateless) 서비스는 scale-out이 쉽지만, 상태 저장(stateful) 데이터 시스템을 여러 노드로 나누면 복잡도가 크게 늘어난다. 그래서 확장이 필요해질 때까지 단일 노드로 버티는 것이 일반적인 선택이었다.

## 트레이드오프 · 주의점
- (보충) 모든 상황에 맞는 확장 아키텍처는 없다. 어떤 연산이 흔하고 드문지, 즉 부하 매개변수에 대한 가정 위에서 설계된다. 가정이 틀리면 확장 노력은 낭비된다.
- (보충) 수동 확장은 단순하고 예측 가능하며, 탄력적 확장은 부하 예측이 어려울 때 유리하다.

## 관련 개념
- [[신뢰성 (Reliability)]] — 부하가 늘어도 올바르게 동작해야 한다
- [[유지보수성 (Maintainability)]] — 확장을 위해 복잡해진 시스템은 유지보수가 어렵다
- [[리액티브 시스템 (Reactive Systems)]] — 리액티브 선언문의 탄력성(elastic)이 같은 개념
- [[가비지 컬렉션 (Garbage Collection)]] — GC 정지는 꼬리 지연의 흔한 원인
- [[중심 극한 정리 (Central Limit Theorem)]] — 응답 시간처럼 꼬리가 긴 분포는 평균 하나로 요약하면 안 된다
- 이후 후보: [[복제 (Replication)]], [[파티셔닝 (Partitioning)]] (DDIA 5·6장)

## 면접 포인트
- "평균 응답 시간 대신 백분위를 보는 이유는?" → 분포가 치우쳐 있어 평균이 실제 경험을 가린다. p99는 꼬리 지연을 드러낸다.
- "scale-up과 scale-out의 트레이드오프는?" → 단순성·비용 한계 vs 분산 복잡도. stateless와 stateful에 따라 난이도가 다르다.
- "트위터 타임라인 설계" → 팬아웃 on read와 on write, 그리고 혼합형.
