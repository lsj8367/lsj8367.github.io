# 관계형 모델과 문서 모델 (Relational vs Document Model)
> 데이터를 테이블(관계)로 표현하는 관계형 모델과, JSON 같은 자기 완결적 문서로 표현하는 문서 모델의 비교.

## 핵심
- 관계형 모델의 목표: **정리된 인터페이스 뒤로 구현 세부사항을 숨기는 것.**
- 1970~80년대에는 네트워크 모델과 계층 모델이 주요 대안이었지만 관계형 모델이 우위를 점했다.

## 세부 / 동작 방식
### NoSQL의 탄생
- NoSQL이라는 이름은 특정 기술을 가리키지 않아 적절하지 않지만, 밋업·컨퍼런스·커뮤니티에서 빠르게 퍼져 굳어졌다.
- 채택 이유:
  1. 대규모 데이터셋이나 매우 높은 쓰기 처리량을 관계형 DB보다 쉽게 달성하는 확장성
  2. 상용 DB보다 무료 오픈소스 선호
  3. 관계형 모델이 지원하지 않는 특수 질의
  4. 관계형 스키마의 제약에 대한 불만, 더 동적이고 표현력 있는 데이터 모델에 대한 요구

### 객체 관계형 불일치 (임피던스 불일치)
- 대부분의 애플리케이션은 객체지향 언어로 개발되는데, 데이터를 테이블에 저장하려면 객체를 테이블에 짜맞추는 변환 계층이 필요하다. 이를 **임피던스 불일치(impedance mismatch)** 라 한다.
- (보충) ORM(JPA/Hibernate 등)이 이 변환 코드를 줄여 주지만 차이를 완전히 숨기지는 못한다.

### 문서 모델과 비교 (보충)
| | 관계형 | 문서 |
|---|---|---|
| 일대다(트리 구조) | 여러 테이블 + 조인 | 문서 하나에 중첩. **지역성(locality)** 이 좋아 한 번에 읽기 |
| 다대일·다대다 | 외래 키 + 조인으로 자연스러움 | 조인 지원이 약해 애플리케이션에서 처리 |
| 스키마 | 쓰기 시 스키마(schema-on-write) | 읽기 시 스키마(schema-on-read) |
| 적합한 경우 | 관계가 많은 데이터 | 문서 단위로 통째로 읽고 쓰는 데이터 |

- (보충) 두 모델은 서로 수렴 중이다. 관계형 DB는 JSON 컬럼을 지원하고, 문서 DB는 조인 비슷한 기능을 추가하고 있다.

## 트레이드오프 · 주의점
- (보충) 데이터 모델 선택은 "어느 쪽이 낫다"가 아니라 **데이터 간 관계의 형태**로 결정한다.
